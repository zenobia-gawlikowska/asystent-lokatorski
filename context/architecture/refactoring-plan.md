# Refactoring Plan — Asystent Lokatorski

Every item below was verified against the actual repository state (file contents, git history, or grep results) before being included. Generic advice not grounded in something observed in this codebase was deliberately left out.

## Do first

### 1. `AGENTS.md` and `CLAUDE.md` document a removed auth system as if it still exists

**What's wrong**: `CLAUDE.md`'s "Architecture" section states the stack is "Astro 6 SSR app with React 19 islands, Tailwind 4, **Supabase auth**, and shadcn/ui components," and its "Auth flow" subsection documents `src/lib/supabase.ts`, `src/middleware.ts`, `PROTECTED_ROUTES`, API endpoints at `src/pages/api/auth/{signin,signup,signout}.ts`, auth pages at `src/pages/auth/{signin,signup,confirm-email}.astro`, and a protected page example at `src/pages/dashboard.astro`. None of these files exist — confirmed via `find src -type f`. The CI section of the same file also states the workflow "runs lint + build on every push and PR to **master**" and "requires `SUPABASE_URL` and `SUPABASE_KEY` repository secrets" — the real `ci.yml` targets `main`, runs lint → **test** → build, and has no Supabase secrets. `AGENTS.md`, by contrast, is largely accurate and already states "No authentication or server-side user state... Supabase auth scaffolding was deliberately removed" — so the two root docs actively contradict each other on the most basic architectural fact of the app.

**Why it matters**: This is the exact drift the certification is designed to catch — code and its own governing AI-context file disagree about whether auth exists. Anyone (human or agent) reading `CLAUDE.md` in isolation would scaffold new work assuming Supabase auth is live, wire up `context.locals.user`, or reference a `dashboard.astro` that doesn't exist. It also directly undercuts confidence in the access-control Open Question in `prd.md` — a reviewer skimming `CLAUDE.md` might wrongly conclude auth exists and the access-control gap is already closed.

**Concretely what to change**: Rewrite `CLAUDE.md`'s "Architecture" and "Auth flow" sections to match `AGENTS.md`'s already-correct statement that no auth exists. Fix the CI section (branch name `main` not `master`; add the `test` step; remove the Supabase-secrets requirement). Decide whether `CLAUDE.md` should be deleted in favor of the more accurate `AGENTS.md`, or kept and corrected — having two root AI-context files that disagree is itself a problem independent of which one is right.

### 2. `README.md.scaffold` is a dead file, checked into the repo, that documents the same removed Supabase auth system

**What's wrong**: `README.md.scaffold` is the original 10x-astro-starter template README, preserved verbatim by the bootstrapper when it detected a conflict with the pre-existing `README.md` (documented in `context/changes/bootstrap-verification/verification.md`: "README.md already existed in cwd → scaffold copy preserved as README.md.scaffold"). It still lists "Supabase - Authentication and backend-as-a-service" as part of the tech stack and describes Cloudflare Pages deployment. It has never been resolved — `context/changes/bootstrap-verification/verification.md`'s own "Next steps" says "Review README.md.scaffold vs README.md and decide if starter content should replace the placeholder," and that review evidently never happened (the file is still present, unmodified, in the current tree).

**Why it matters**: It's a second, lower-visibility copy of the same stale-auth-documentation problem as item 1, sitting in the repo root where any contributor or grader might open it. It also has no functional purpose — nothing in the codebase references it.

**Concretely what to change**: Delete `README.md.scaffold`. The real `README.md` is accurate and has already superseded it (confirmed by reading both — `README.md` correctly describes the actual multilingual wizard, no-login, Cloudflare Workers deployment).

## Can wait

### 3. `src/data/tree.ts` is an 835-line single file holding all case-type data, in all 6 languages, inline

**What's wrong**: Every `CaseType`/`Stage`/`SubType`/`Document` node — including every string in all 6 languages — lives in one file. Two case types (`wypowiedzenie`'s `termin-minal` stage and the standalone `dzika-eksmisja` case type) contain byte-for-byte duplicated `Stage`/`Document` objects (`bezprawne-odciecie-mediow-sub` / `bezprawne-odciecie-mediow`, `najscie-w-lokalu-sub` / `najscie-w-lokalu`, `postepowanie-umorzone-sub` / `postepowanie-umorzone` — confirmed by reading the file: these are the same Polish/Ukrainian/Russian/English/Spanish/French copy and the same `filename`, just under two different parent IDs). This is presumably intentional (commit `4c49cd0`, "consolidate odciecie-mediow into dzika-eksmisja," suggests the sub-tree under `wypowiedzenie` was kept reachable from two entry points rather than one canonical location), but it means any future edit to that content (a legal citation update, a translation fix) must be made in two places or will silently drift.

**Why it matters**: `context/foundation/tech-stack.md` itself anticipates the multi-city direction ("no auth, payments, realtime, AI ... in MVP scope — the Supabase layer ships dormant and becomes the integration point when the future LLM-assisted eligibility capability lands," and the `DecisionTree = City[]` type is already multi-city-shaped per `src/data/types.ts`). Adding a second city today means either duplicating the 835-line pattern into a second equally large block in the same file, or restructuring first. The duplicated `dzika-eksmisja`/`termin-minal` subtree above is a live example of what happens without a shared-fragment mechanism.

**Concretely what to change**: Before a second city is added, split `tree.ts` per case type (e.g. `src/data/case-types/wypowiedzenie.ts`, `podwyzka-czynszu.ts`, etc., re-exported from an index), and extract the duplicated `bezprawne-odciecie-mediow`/`najscie-w-lokalu`/`postepowanie-umorzone` stages into a single shared constant referenced from both `wypowiedzenie`'s subtree and the standalone `dzika-eksmisja` case type, rather than two copies of the same object literal. This is explicitly a "can wait" — the file is unwieldy but not currently broken, and premature splitting before a second city is scoped risks guessing wrong about the right seam.

### 4. FR-numbering is scattered as inline code comments, not centralized

**What's wrong**: FR-001 and FR-002 exist only as one-line comments at their respective call sites (`src/data/types.ts:56`, `src/components/Wizard.tsx:320`) — there was no central FR registry anywhere in the repo before this pass. `context/foundation/prd.md` (written in this same pass) now centralizes FR-001 through FR-008, but the inline comments themselves are still the only place the *code* self-documents which requirement it satisfies.

**Why it matters**: This is the origin of the doc/code drift risk generally — a requirement recorded only as a scattered inline comment has no single place a reviewer or future contributor checks to see the full list, and nothing enforces that a new FR gets both a code comment and a PRD entry. It's not currently causing a concrete bug, which is why this is "can wait" rather than "do first" — but it's worth naming as the pattern to fix going forward, now that `prd.md` exists as the canonical FR list.

**Concretely what to change**: For any FR added after this PRD exists, add the code comment AND a `prd.md` entry in the same change, and treat `prd.md`'s Functional Requirements section — not scattered comments — as the source of truth going forward. No code change is proposed here since the existing FR-001/FR-002 comments are accurate and harmless as supplementary in-context pointers.

### 5. `Banner.astro` and `LibBadge.astro` are dead code left over from the starter scaffold

**What's wrong**: `grep -rn "Banner|LibBadge" src/ --include="*.astro" --include="*.tsx"` (excluding their own definitions) returns nothing — neither component is imported or rendered anywhere in the app. Both are generic starter-template components (a colored alert banner, a "library badge" chip) with no KOPL-specific purpose.

**Why it matters**: Low severity — they don't affect behavior or bundle size in a meaningful way (Astro components are only included in the build if imported), but they're dead weight that could mislead a future contributor into thinking they're part of the live UI, and they're not caught by the current lint config (`no-unused-vars` catches unused *variables*, not unused *files*).

**Concretely what to change**: Delete `src/components/Banner.astro` and `src/components/ui/LibBadge.astro` unless there's a near-term plan to use them (e.g. `Banner.astro` as the vehicle for a future "this is not legal advice" disclaimer, which would be a reasonable use — but that should be a deliberate decision, not passive retention).

### 6. `wizard-state.ts` test coverage stops at the pure-function layer; `Wizard.tsx` itself is untested

**What's wrong**: The 29 Vitest tests in `tests/wizard-state.test.ts` thoroughly cover `stepCount`, `stepNumber`, `appendStep`, `popStep`, `resetSteps`, and `deriveWizardNodes` — all pure functions with no DOM dependency. There is no test at all for `Wizard.tsx`'s React rendering (tile rendering per step, the language switcher's `localStorage` read/write and `document.documentElement.lang` mutation, the axe-core dev-only integration, or the download link's `href`/`download` attributes), and no test that validates `tree.ts`'s actual content (e.g., that every `Document.filename` referenced in the tree has a corresponding file under `public/documents/warszawa/`, or that every `LocalizedString` object has all 6 language keys populated — several `note` fields in `tree.ts` are optional and inconsistently present, which is fine, but nothing currently checks that required fields like `name`/`description`/`label` are complete for all 6 languages across all 5 case types).

**Why it matters**: The pure-function extraction (this repo's own big testing win, per commit `cd7a539`) was the right first move, but it leaves the two riskiest surfaces unchecked: (a) the actual legal-document content data — a missing or misspelled `filename` would only surface as a broken download link discovered by a real tenant, not by CI; (b) the React component wiring — a regression in `LanguageSwitcher` or the axe integration would pass `npm test` today.

**Concretely what to change**: Add a small data-integrity test (plain Node/Vitest, no DOM needed) that walks `tree.ts` and asserts every `Document.filename` resolves to a real file under `public/`, and that every `LocalizedString` in the tree has all 6 `Lang` keys with non-empty values. This is higher-leverage than component testing for this specific app, since a broken filename directly breaks the tenant-facing outcome the app exists for. Component-level testing (React Testing Library or similar) is a reasonable next step after that, but lower priority given the component logic is thin and already delegates its interesting logic to the tested `wizard-state.ts`.
